# Qualitative Analysis

## Purpose

`qualitative-analysis` translates a design-ready qualitative study into a transparent and scientifically defensible analytic process.

Its central question is:

> How should qualitative material be interpreted, coded, compared, developed into categories, themes, concepts, mechanisms, narratives, or theory so that the analysis answers the research question while preserving context, meaning, reflexivity, and methodological coherence?

This skill supports analysis of:

- interviews;
- focus groups;
- field notes;
- observations;
- documents;
- narratives;
- reflective journals;
- open-ended survey responses;
- policy texts;
- visual or multimodal qualitative material;
- qualitative components of mixed-method studies.

It does not force every qualitative study into thematic analysis.

It does not convert qualitative rigor into statistical significance.

It does not treat software-generated code counts as interpretation.

---

# Core Principle

Use:

> Epistemic purpose before coding method. Meaning before frequency. Context before decontextualization. Interpretation before software.

A qualitative analysis should follow:

```text
Research Question
      ↓
Epistemic / Interpretive Purpose
      ↓
Qualitative Design
      ↓
Data Source and Context
      ↓
Unit of Meaning
      ↓
Analytic Orientation
      ↓
Coding / Interpretation
      ↓
Categories / Themes / Concepts / Theory
      ↓
Negative Cases / Reflexivity / Audit
      ↓
Integrated Interpretation
```

Do not begin with software menus.

# Thematic Analysis Guard

Do not use "thematic analysis" as a generic label for all qualitative coding.

Specify:

- reflexive thematic analysis;
- codebook thematic analysis;
- coding-reliability thematic analysis;
- or another clearly defined approach.

Different forms make different assumptions.

---

# Reflexive Thematic Analysis

Appropriate when:

- themes are interpreted as analytic constructions;
- researcher reflexivity is central;
- coding is iterative;
- multiple coders are not required for statistical agreement;
- meaning may be semantic or latent.

Typical stages may include:

```text
Familiarization
      ↓
Initial Coding
      ↓
Candidate Theme Development
      ↓
Theme Review
      ↓
Theme Definition
      ↓
Analytic Narrative
```

Do not reduce reflexive thematic analysis to inter-rater reliability.

---

# Codebook Thematic Analysis

May be appropriate when:

- a shared coding framework is useful;
- teams require structured coding consistency;
- applied or evaluative research requires traceable domains;
- coding is partly deductive.

Codebook development should remain conceptually justified.

---

# Coding Reliability Approaches

When inter-coder consistency is itself part of the methodological approach, define:

- codebook;
- coder training;
- coding unit;
- calibration sample;
- discrepancy handling;
- agreement metric if appropriate.

Do not impose reliability metrics on approaches that reject coding as a fixed measurement act.

# Qualitative Content Analysis

May be:

- conventional;
- directed;
- summative;
- inductive;
- deductive.

Clarify whether the goal is:

- manifest content;
- latent content;
- categories;
- concepts;
- frequency-supported interpretation.

Do not confuse content frequency with conceptual importance.

# Grounded Theory

Use only when the purpose is theory generation.

Core features may include:

- iterative data collection and analysis;
- constant comparison;
- memoing;
- theoretical sampling;
- category development;
- theoretical integration.

Do not label ordinary interview coding as grounded theory.

---

# Constant Comparison

Compare:

- incident with incident;
- incident with code;
- code with code;
- code with category;
- category with category;
- case with case.

Use comparison to refine conceptual boundaries.

---

# Theoretical Sampling

In grounded theory, sampling may evolve in response to emerging categories.

Do not treat a fully fixed convenience sample as theoretical sampling.

---

# Saturation in Grounded Theory

Theoretical saturation concerns category development and theoretical sufficiency.

It is not identical to code repetition.

---

# Phenomenological Analysis

Use when the study seeks lived experience.

Preserve:

- embodied meaning;
- temporality;
- relationality;
- context;
- participant lifeworld.

Do not collapse phenomenology into generic topic counting.

---

# Interpretative Phenomenological Analysis

IPA commonly emphasizes:

- idiographic case analysis;
- detailed participant experience;
- interpretative engagement;
- case-by-case progression before cross-case patterns.

Do not use very broad heterogeneous samples without justification.

---

# Narrative Analysis

Use when:

- temporal sequence;
- identity;
- plot;
- turning points;
- personal meaning;
- narrative structure;

are central.

Do not fragment narratives so aggressively that temporal coherence disappears.

---

# Discourse Analysis

Use when the RQ concerns:

- language use;
- social construction;
- power;
- positioning;
- discourse practices;
- institutional language.

Do not treat discourse analysis as ordinary thematic coding.

---

# Conversation Analysis

Requires detailed attention to:

- turn-taking;
- sequence;
- pauses;
- repair;
- overlap;
- interactional organization.

Ordinary verbatim transcription may be insufficient.

---

# Case Study Analysis

Preserve:

- case boundaries;
- context;
- within-case analysis;
- cross-case comparison when relevant;
- multiple evidence sources.

Do not dissolve cases into one pooled theme set if case integrity matters.

---

# Cross-Case Analysis

Possible strategies include:

- case matrices;
- pattern matching;
- explanation building;
- contrast cases;
- replication logic.

---

# Process Analysis

When the RQ asks how something unfolds, preserve:

- sequence;
- stages;
- transitions;
- triggers;
- mechanisms;
- context.

Avoid purely static thematic summaries.

---

# Realist-Informed Analysis

When mechanism-context-outcome reasoning is central, consider:

```text
Context
   ↓
Mechanism
   ↓
Outcome
```

Do not treat observed association as proof of mechanism.

---

For documents define:

- document type;
- provenance;
- author / institution;
- date;

- purpose;
- version;
- context;
- authenticity.

---

# Policy Text Analysis

Distinguish:

- policy content;
- policy intent;
- implementation evidence;
- observed outcome.

Textual policy analysis alone does not establish policy impact.

---

# Open-Ended Survey Responses

These can support qualitative analysis, but depth may be limited.

Do not claim interview-level interpretive richness from one-line responses unless the data actually support it.

# Multimodal Analysis

# Translation of Qualitative Data

When data are collected in one language and analyzed or reported in another, preserve:

- source language;

- translator role;
- culturally specific terms;

# Translation Timing

Possible strategies:

- analyze source language first;
- translate full transcripts;
- translate coded excerpts;
- bilingual coding.

# Anonymization

Protect identities while preserving analytically important context.

Avoid removing so much contextual detail that interpretation becomes meaningless.

# Unit of Meaning

Possible units include:

- word;
- phrase;
- sentence;
- turn;
- paragraph;
- event;
- episode;
- narrative segment;
- whole case;
- document section.

---

# Semantic vs Latent Coding

Semantic coding addresses explicit meaning.

Latent coding interprets underlying assumptions, concepts, or patterns.

State which level is intended.

---

# Inductive Coding

Inductive coding is data-responsive.

It is not theory-free.

Researchers still bring perspectives and assumptions.

---

# Deductive Coding

Deductive coding may derive from:

- theory;
- framework;
- prior evidence;
- implementation model;
- policy criteria;
- interview domains.

Leave room for unexpected data when scientifically appropriate.

---

# Hybrid Coding

Hybrid approaches combine deductive and inductive coding.

Document which codes were:

- a priori;
- emergent;
- revised;
- merged;
- retired.

---

# Descriptive Codes

Capture surface topic or content.

Example:

`training difficulty`

---

# Interpretive Codes

Capture analytic meaning.

Example:

`institutional support failure`

Do not confuse topic labels with final themes.

---

# In Vivo Codes

Use participant language when it captures important meaning.

Do not overuse in vivo coding if analytic abstraction is required.

---

# Process Codes

Useful for action or change.

Examples:

- adapting;
- resisting;
- negotiating;
- learning;
- avoiding.

---

# Values / Belief Codes

Useful when beliefs, norms, values, or attitudes are central.

---

# Emotion Codes

Use when emotional experience is analytically relevant.

---

# Structural Codes

May follow interview-guide domains.

Useful for organizing large applied datasets.

---

# Coding Granularity

Avoid:

- coding every sentence mechanically;
- coding whole transcripts with one broad label.

Granularity should support the RQ.

A codebook may include:

# Coding Iteration

# Double Coding

Double coding may be useful for:

- team calibration;
- shared codebook refinement;
- reliability-focused designs;
- training.

It is not universally required.

---

# Inter-Coder Agreement Guard

Do not treat kappa as a universal qualitative quality criterion.

Use only when agreement is methodologically meaningful.

---

# Disagreement

Disagreement may reveal:

- unclear code definitions;
- conceptual ambiguity;
- different interpretive positions;
- overlooked context.

Do not resolve all disagreement by majority vote automatically.

---

# Memos

Memoing should capture:

- code interpretation;
- category development;
- theoretical ideas;
- negative cases;
- decisions;
- reflexivity;
- emerging relationships.

# Memo Types

Possible memo types:

- case memo;
- code memo;

---

# Case Memo

Summarize a participant or case while preserving:

- context;

- distinctive features.

---

# Category Development

Categories are broader conceptual groupings than individual codes.

Evaluate:

- internal coherence;
- distinction from other categories;
- explanatory value;
- relation to RQ.

---

# Theme Development

A theme should express a meaningful pattern relevant to the RQ.

A strong theme is not merely:

- a topic;
- a section of the interview guide;
- a frequently mentioned word.

---

# Theme Quality

Assess:

- central organizing concept;
- coherence;
- boundaries;
- data support;
- analytic depth;
- relevance to RQ;
- distinction from other themes.

---

# Theme Naming

Prefer names that communicate analytic meaning.

Weak:

`Training`

Stronger:

`Training as episodic support rather than sustained professional learning`

---

# Theme Definition

For each theme:

```yaml
theme:
  name:
  central_organizing_concept:
  included_patterns:
  excluded_patterns:
  related_codes:
  negative_cases:
  supporting_cases:
  interpretive_claim:
```

---

# Subthemes

Use subthemes when they clarify meaningful variation.

Do not create subthemes merely to organize long lists.

---

# Theme Hierarchy Guard

Avoid deep nested hierarchies without analytic purpose.

---

# Frequency Guard

A theme is not important only because it is frequent.

Rare but conceptually critical cases may matter.

---

# Quantification of Qualitative Data

Counts may sometimes support:

- transparency;
- prevalence-like description within a bounded corpus;
- codebook analysis;
- mixed methods.

But counts do not replace interpretation.

---

# "Most Participants" Guard

Use frequency language only when the data support it.

Avoid vague claims such as:

- many;
- most;
- almost all;

without a defensible basis.

---

# Negative Cases

Actively seek data that challenge:

- emerging themes;
- causal explanations;
- dominant narratives;
- theoretical assumptions.

Do not hide contradictory cases.

---

# Deviant Cases

Use deviant or disconfirming cases to refine:

- boundaries;
- mechanisms;
- context;
- exceptions.

---

# Contradiction

Contradiction can be analytically productive.

Do not force all data into one coherent story.

---

# Variation

Analyze meaningful variation by:

- participant type;
- setting;
- time;
- case;
- experience;
- exposure;
- institutional context.

Avoid subgroup comparison without sufficient qualitative basis.

---

# Within-Case Analysis

Preserve each case before cross-case abstraction when case trajectory matters.

---

# Cross-Case Matrix

Possible structure:

|---|---|---|---|---|---|

---

# Temporal Analysis

When change over time matters, preserve:

- before;
- transition;
- after;

- recurrence;
- adaptation.

---

# Mechanism Development

Qualitative data may support mechanism hypotheses through:

- sequence;
- actor reasoning;
- context;
- process;
- repeated pattern;
- negative case.

Do not claim causal proof from narrative alone.

---

# Theory Use

Theory can be:

- sensitizing;
- deductive;
- explanatory;
- interpretive;
- generative.

State its role.

---

# Theory-Driven Analysis

When theory is used deductively, preserve room for:

- non-fitting data;
- theory extension;
- contradictory evidence;
- contextual adaptation.

---

# Theory Generation

When building theory, move from:

```text
Codes
  ↓
Categories
  ↓
Relationships
  ↓
Core Concepts
```

# Claim Strength

Classify qualitative claims cautiously:

- strongly supported;
- recurrent;
- context-specific;
- tentative;
- contradictory;
- emerging.

Do not use statistical confidence language automatically.

---

# Overgeneralization Guard

Do not write:

> Participants believe...

when only one participant expressed the view, unless explicitly framed as an individual case.

---

# Causal Language Guard

Qualitative data can illuminate mechanisms and perceived causality.

Do not claim population-level causal effect without appropriate design.

---

# Experience vs Fact

Participant reports are evidence about:

- experience;
- perception;
- interpretation;
- reported events.

They may not independently verify external factual claims.

---

# Reported Practice vs Observed Practice

- what participants say they do;
- what was directly observed.

---

# Social Desirability

Consider how role, setting, interviewer, and topic may shape responses.

---

# Power Dynamics

Analyze whether:

- hierarchy;
- profession;
- age;

# Relationship with Analysis Planner

`analysis-planner` defines the qualitative analytical problem and routes to this skill.

`qualitative-analysis` determines and executes the qualitative interpretive strategy.

Use:

```text
analysis-planner
      ↓
qualitative-analysis
```

---

# Relationship with Methodology Architect

The qualitative analysis must remain coherent with the chosen study design.

Do not use grounded-theory analysis for a study designed only as descriptive qualitative research unless the design is explicitly revised.

---

# Relationship with Sampling Strategy

Sampling logic affects:

- case variation;
- information power;
- theoretical sampling;
- transferability.

Do not judge qualitative sample adequacy by statistical power.

---

# Relationship with Instrument Design

Interview guides, observation tools, and document-extraction forms shape the data available for analysis.

The analytic process must not silently redefine the measurement or elicitation purpose.

---

# Relationship with Protocol Builder

`protocol-builder` defines how qualitative material was produced.

Analysis must respect:

- interview mode;
- setting;
- recording;
- transcription;
- participant flow;
- field-note procedures.

---

# Relationship with Theoretical Framework

Theory may serve as:

- sensitizing concept;
- deductive framework;
- interpretive lens;
- explanatory model.

Do not force data to confirm theory.

---

# Relationship with Conceptual Framework

A conceptual framework may guide coding domains.

Emergent evidence can refine the framework.

Do not hide framework-inconsistent data.

---

# Relationship with Mixed-Method Analysis

When qualitative findings are one strand of a mixed-method design, pass them to:

`mixed-method-analysis`

for integration.

---

# Relationship with Statistical Method Selector

Do not route qualitative inference to statistical method selection merely because code frequencies are available.

---

# Relationship with Result Interpreter

`result-interpreter` integrates findings into scientific conclusions.

Do not move to interpretation before themes, categories, cases, and boundaries are sufficiently established.

---

# User-Friendly Behavior

Prefer:

> Your question asks how teachers experience implementation barriers. A reflexive thematic analysis can fit if the aim is interpretive pattern development, but we should not require inter-rater kappa as if coding were a fixed measurement process.

Or:

> Because this is a grounded-theory design, the analysis should use constant comparison, memoing, category development, and theoretical sampling rather than stopping at a list of themes.

Or:

> These open-ended survey responses are useful, but their brevity limits phenomenological depth. We can analyze recurrent categories without overstating them as rich lived-experience accounts.

---

# Avoid These Behaviors

Do not:

- call all qualitative analysis thematic analysis;
- count words and call them themes;
- use software-generated clusters as final interpretation;
- require kappa for every qualitative approach;
- claim saturation without documented logic;
- equate frequency with importance;
- hide negative cases;
- fragment narratives when temporal coherence matters;
- claim causal effects from participant perceptions alone;
- use participant quotes without analytic interpretation;
- select only dramatic quotes;
- erase context during coding;
- ignore researcher reflexivity;
- treat member checking as proof of truth;
- claim statistical generalizability from purposive samples;
- force theory onto contradictory data;
- label ordinary coding as grounded theory;
- label topic summaries as theory;
- use AI-generated themes without researcher verification;
- allow software to determine the analytic orientation.

---

# Stop Conditions

Do not classify qualitative analysis as ready when:

- RQ is unclear;
- qualitative design is unresolved;
- data provenance is unknown;
- transcription quality is inadequate for the chosen analysis;
- unit of meaning is undefined;
- analytic orientation conflicts with the research design;
- coding has no conceptual relationship to the RQ;
- theme claims cannot be traced to data;
- negative cases are ignored;
- reflexive influence is materially relevant but undocumented;
- theory is being imposed without room for contradiction;
- qualitative findings are reduced to counts without interpretive justification;
- software or AI output is being treated as analysis without human review.

Use:

- `RETURN_TO_ANALYSIS_PLANNER`
- `RETURN_TO_METHODOLOGY_ARCHITECT`
- `RETURN_TO_PROTOCOL_BUILDER`
- `RETURN_TO_SAMPLING_STRATEGY`
- `RETURN_TO_INSTRUMENT_DESIGN`
- `QUALITATIVE_ANALYSIS_REQUIRES_REVISION`

when appropriate.

---

# Success Criterion

`qualitative-analysis` succeeds when a design-ready qualitative study has been translated into a transparent, context-sensitive, reflexive, and methodologically coherent analytic process that explicitly defines the epistemic purpose, analytic orientation, data source, transcription and translation status, unit of meaning, coding strategy, codebook or interpretive process where appropriate, memoing, case comparison, category and theme or theory development, negative-case analysis, reflexivity, triangulation, saturation or information-power logic, trustworthiness strategy, audit trail, software role, and downstream handoff to `mixed-method-analysis` or `result-interpreter`, without reducing qualitative inquiry to frequency counting, inter-rater metrics, software output, AI-generated labels, generic themes, or methodological ritual.
